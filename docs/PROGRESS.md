## 2026-08-19 — Build reproducibility and dependency hygiene

### Product-priority decision

The recovery subsystem now has a durable crash-safe continuation handoff. Further continuation-consumer hardening is intentionally parked until an end-to-end product slice requires it. Build reproducibility was the next blocking foundation issue because CI was resolving a fresh dependency graph on every run and the previous graph contained a concrete AWS SDK peer mismatch.

### Normal change

- Root TypeScript and Vitest are pinned to the exact versions already exercised by the prior green CI: `typescript@5.9.3` and `vitest@3.2.7`.
- Direct `@aws-sdk/client-dynamodb` is aligned to `3.1111.0`. The lock graph generated by CI shows `@aws-sdk/lib-dynamodb@3.1103.0` now consuming `@aws-sdk/util-dynamodb@3.996.9` with a satisfied `@aws-sdk/client-dynamodb@^3.1111.0` peer instead of the previous mismatch.
- CI #127 intentionally generated the pnpm 10.15.0 lock graph and failed only because that graph was not yet pinned. The former DynamoDB peer warning disappeared. The remaining two warnings are deprecated transitive compatibility packages (`@aws-sdk/protocol-http@3.374.0` and `@aws-sdk/signature-v4@3.374.0`) pulled by the current AgentCore stack; they are not peer-resolution failures and are not suppressed.
- CI #127 also exposed a real runtime-contract mismatch: the resolved `vite@7.3.6` requires Node `>=22.12.0`, while the repository still declared `>=22.0.0`. The engine floor is corrected to `>=22.12.0`, and CI uses the exact Node `22.23.2` version that generated the pinned graph.

### Corrective lock strategy

The connector runtime cannot transfer a generated GitHub Actions workspace file directly into Git data, so the corrective build uses CI #127's immutable job log (`96040770342`) as the bootstrap source for the exact generated lock snapshot instead of re-resolving dependencies. CI has read-only `actions:read` + `contents:read`, extracts only the bounded `pnpm-lock.yaml` section, validates its start/end and the corrected DynamoDB resolution, then installs with `pnpm install --frozen-lockfile`.

This is deterministic for the pinned source snapshot and does not upload an Actions artifact, but it is intentionally recorded as a bootstrap mechanism rather than the ideal final repository shape: GitHub workflow-log retention can eventually remove the source. A conventional checked-in `pnpm-lock.yaml` should replace this source-backed bootstrap when the development runtime can materialize the generated file directly. Until then, CI fails closed if the source cannot be retrieved or its expected structure changes; it never silently falls back to fresh resolution.

### Security / tenancy / side effects

- This slice changes dependency resolution and CI only. Browser execution authority, tenant scoping, credential storage, retry behavior, schedules, external side effects, and human recovery semantics are unchanged.
- Workflow permissions are read-only. No package, secret, write token, build artifact upload, or runtime cloud permission was added.
- The pinned lock snapshot contains package metadata/integrity values only; it contains no user data or platform credentials.
- CI no longer converts a dependency warning into a pass by ignoring it; the incompatible DynamoDB peer was corrected at the manifest boundary.

### Cost / observability / operations

- No Actions artifact is emitted, avoiding additional artifact-storage pressure.
- The exact dependency graph is reused for frozen installs rather than resolved afresh each run.
- CI prints the materialized lock SHA-256, making graph identity visible in run logs.
- If the bootstrap source expires, CI fails before install rather than drifting to a new package graph.

## Recovery boundary intentionally parked

The current recovery continuation record is a durable handoff, not action authority. A future continuation consumer must remain idempotent before automatic post-reconstruction execution is enabled. `AMBIGUOUS` remains human-attention only, and `DEFINITELY_NOT_APPLIED` remains non-executable until an explicit proof-of-absence/idempotency contract exists. No additional recovery micro-hardening should preempt the product milestones above unless CI or an end-to-end slice exposes a concrete correctness defect.
